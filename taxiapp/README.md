# Бахром Такси — два режима, реальный backend

Android-приложение на Kotlin + Jetpack Compose: один и тот же apk открывается либо в
режиме **«Я пассажир»**, либо в режиме **«Я водитель»** — выбор на стартовом экране.
При первом входе в режим приложение просит имя, регистрирует его на backend и
дальше работает через реальные HTTP/WebSocket-запросы — это уже не локальная
имитация на одном устройстве, два разных телефона видят друг друга по-настоящему.

## Кто считает цену и почему

Цену считает **сервер**, а не пассажир и не водитель, и не сам телефон — так делают
Яндекс.Такси, Uber и большинство агрегаторов:
- если цену называет водитель — начинается торг и обман на месте;
- если цену предлагает пассажир (модель InDrive) — сложнее гарантировать поездку и
  прозрачно считать комиссию агрегатора как фиксированный процент.

Экран пассажира до заказа показывает **оценочную** цену (формула ниже, коэффициент
спроса = 1.0, локально в `PricingEngine` — только предпросмотр), а окончательную,
с реальным коэффициентом спроса на момент заказа, возвращает backend в ответе на
`POST /rides` — она и есть авторитетная.

Формула (совпадает с той, что должен считать backend — см. «Backend» ниже):

```
итого = round_to_10( max(99 + км × 14 + минуты × 4, 149) × коэффициент_спроса )
комиссия = округлить_до_копеек(итого × 0.01)
```

## Комиссия агрегатора

1% от суммы каждой поездки — начисляется на backend при завершении поездки, водитель
видит баланс «к оплате» и гасит его отдельной кнопкой.

## Backend

Отдельный сервис (не в этом репозитории) — Node.js на VPS пользователя. Контракт,
который ожидает мобильное приложение (`network/ApiService.kt`, `network/Dto.kt`):

- `POST /auth/register` `{role: "passenger"|"driver", name, carMake?, carColor?,
  carPlate?, clickHandle?}` → `{token, userId, role, name}`. Поля `carMake/carColor/
  carPlate/clickHandle` осмысленны только для `role: "driver"` — backend должен их
  сохранить в профиле водителя (пока необязательные, приложение их не требует).
- `POST /rides` (Bearer-токен) `{fromAddress, toAddress, distanceKm, durationMin,
  paymentMethod: "CASH"|"CARD"|"CLICK"}` → объект поездки с полем `price` (`baseFare,
  distanceCost, timeCost, demandFactor, total, commission, driverPayout`), `status`
  (`SEARCHING|ACCEPTED|IN_PROGRESS|COMPLETED|CANCELLED`) и `paymentMethod` (эхо того,
  что прислал пассажир)
- `GET /rides/pending` → список заказов в статусе `SEARCHING`
- `POST /rides/{id}/accept` / `/start` / `/complete` — при `accept` backend должен
  проставить в объект поездки `driverClickHandle` из профиля принявшего водителя
  (если у него он заполнен) — так пассажир увидит, куда переводить, если выбрал
  оплату Click
- `POST /drivers/{id}/online` `{online}`
- `GET /drivers/{id}/commission` / `POST /drivers/{id}/commission/pay` → `{owed, paid}`
- WebSocket `wss://.../ws`: `{"type":"ride.created","ride":{...}}` /
  `{"type":"ride.updated","ride":{...}}` — объект `ride` тот же, что и в ответах REST
  (с `paymentMethod`/`driverClickHandle`)

Это аддитивные поля поверх уже работающего контракта — если backend просто
проигнорирует их, старая часть (создание/приём/статус поездки, комиссия) продолжит
работать как раньше; не будут работать только новые куски UI (номер машины у
пассажира при подтверждении и Click-реквизиты).

Формула `demandFactor` (считает только backend, авторитетный источник — сервер, не
этот репозиторий; здесь зафиксирована для справки, чтобы не разъезжалась при правках):

```js
function demandFactor(pendingOrders, freeDrivers) {
  const ratio = freeDrivers === 0 ? pendingOrders + 1 : pendingOrders / freeDrivers;
  const factor = 1.0 + 0.2 * ratio;
  const clamped = Math.min(2.5, Math.max(1.0, factor));
  return Math.round(clamped * 10) / 10; // округление до 0.1
}
```

`pendingOrders` — заказы в статусе `SEARCHING`. `freeDrivers` — online-водители, у
которых **нет** поездки в статусе `ACCEPTED`/`IN_PROGRESS` прямо сейчас (не просто
online — занятый поездкой водитель не свободен).

Адрес — `network/NetworkConfig.kt` (`BASE_URL`, `WS_URL`). Если backend в итоге называет
поля/пути иначе — поправить нужно только `NetworkConfig`/`ApiService`/`Dto`, остальной
код (репозиторий, экраны) их не касается.

## Google Maps (адреса, маршрут, расстояние)

Экран пассажира использует Google Maps SDK + Places Autocomplete (выбор адреса из
реальных подсказок — гарантирует, что адрес существует, а не опечатан) + Directions
API (расстояние/время по факту маршрута, полилиния на карте). Всё это требует **вашего
собственного** API-ключа из Google Cloud Console:

1. В [Google Cloud Console](https://console.cloud.google.com/) создайте проект (или
   используйте существующий), включите API: **Maps SDK for Android**, **Places API**,
   **Directions API**.
2. Создайте API-ключ (Credentials → Create Credentials → API key).
3. Ограничьте ключ по приложению (Application restrictions → Android apps):
   - Package name: `com.pit.bahromtaxi`
   - SHA-1: `87:B8:B9:9C:47:2E:1F:D5:25:5D:8E:04:6C:7C:99:58:4D:AC:8D:41`
     (отпечаток `taxiapp/debug.keystore` — фиксированный debug-keystore в этом
     репозитории, специально закоммичен, чтобы SHA-1 не менялся между сборками в CI;
     для release-сборки под своей подписью нужно добавить в ключ ещё и SHA-1 вашего
     `keystore.properties`-кейстора).
4. Ограничьте по API (API restrictions) — только те три API из шага 1, чтобы ключ
   нельзя было использовать для чего-то ещё, даже если он утечёт.
5. Добавьте ключ как секрет репозитория: GitHub → Settings → Secrets and variables →
   Actions → New repository secret → имя `MAPS_API_KEY`, значение — сам ключ. Следующая
   сборка в Actions подхватит его автоматически (`build.yml` передаёт его в Gradle).
6. Для локальной сборки в Android Studio — тот же ключ как Gradle property
   `MAPS_API_KEY` (например, строка `MAPS_API_KEY=...` в `~/.gradle/gradle.properties`,
   не в файле проекта, чтобы не закоммитить случайно).

Без ключа приложение всё равно соберётся (пустая строка — Maps SDK покажет пустую
карту вместо ошибки сборки), но выбрать адрес не получится — при попытке откроется
предупреждение «Карта недоступна: не настроен ключ Google Maps API».

Адрес можно выбрать и текстом (кнопка на карточке «Откуда»/«Куда»), и тапом по точке
на карте (кнопка «На карте») — во втором случае адрес получает `ReverseGeocoder` через
системный `Geocoder` Android (отдельный ключ не нужен, это не Google Maps API-запрос).
«Моё местоположение» (синяя точка) — отдельное разрешение `ACCESS_FINE_LOCATION`,
запрашивается по кнопке на карте, а не автоматически при открытии экрана.

**Что дальше (не сделано в этой версии):** живая точка водителя, двигающаяся навстречу
пассажиру — это отдельная фича, требует от водительского приложения периодически
слать координаты на backend (нужен новый эндпоинт, например `POST /drivers/{id}/location`
+ WebSocket-событие `driver.location`) и рисовать маркер на карте пассажира по этим
обновлениям. Сообщите, когда нужно — подготовлю и код, и промпт для backend.

## Честно о статусе

- **Авторизация упрощённая** — только имя, без пароля/SMS-подтверждения номера. Для
  реального сервиса нужна верификация телефона (иначе кто угодно зарегистрируется
  «водителем»). Требует SMS-шлюза (платный сервис, отдельный аккаунт) — не сделано.
- **Нет истории поездок, рейтингов, профиля, загрузки документов водителя.**
- **Оплата — выбор способа, не реальное списание.** Пассажир выбирает наличные / карту
  водителю / Click, backend это только записывает. Осознанно НЕ добавлено поле для
  номера карты — хранить номер карты текстом небезопасно и нарушает правила платёжных
  систем; для настоящей оплаты картой нужен платёжный шлюз (Payme/Click API как
  провайдер, не как текстовое поле), который токенизирует данные карты так, что
  приложение и backend их вообще не видят.
- **У водителя пока нет карты** — список заказов текстом (адреса, расстояние, цена,
  способ оплаты). Карта с маршрутом до пассажира — часть следующей фичи (живое
  местоположение, см. выше).
- **Чат/видеосвязь между пассажиром и водителем — не сделано.** Чат — отдельная фича
  (нужны новые эндпоинты на backend + экран переписки), видеосвязь — отдельная большая
  интеграция (WebRTC-сервис вроде Agora/Twilio Video), пока не начата.
- **Доставка посылок и грузоперевозки — не сделано.** Это по сути ещё два вида заказа
  со своей формой (фото посылки, отметка «нужны грузчики»), не только надстройка над
  такси — сделаю отдельным заходом, если понадобится.
- **Админ-роль агрегатора (блокировать/удалять пользователей) — не сделано**, требует
  отдельного административного эндпоинта на backend и какого-то интерфейса для него
  (хотя бы веб-страницы, не обязательно в этом Android-приложении).

## Стек

Kotlin, Jetpack Compose (Material 3), Navigation Compose, Retrofit + Moshi + OkHttp
(HTTP и WebSocket), Google Maps SDK + Places + Directions API, `minSdk 24`. Отдельный
Gradle-модуль `:taxiapp` в этом же репозитории — существующее приложение «Призрак»
(`:app`) не затронуто.

## Сборка APK через GitHub Actions

Вкладка **Actions** → **Build APK** → **Run workflow** (или пуш в `main`/`claude/**`).
В артефактах — `bahromtaxi-debug-apk.zip`, внутри `taxiapp-debug.apk`.

## Публикация в RuStore / Google Play — чек-лист

**Техническое:**
1. `applicationId` (сейчас `com.pit.bahromtaxi`, служебный) — сменить на свой уникальный
   перед первой публикацией: изменить нельзя после того, как приложение один раз
   опубликовано под этим id.
2. Подписанная release-сборка: `keytool -genkey -v -keystore bahromtaxi-release.jks
   -keyalg RSA -keysize 2048 -validity 10000 -alias bahromtaxi` (сохранить пароль и файл
   в надёжном месте, НЕ в git), затем скопировать `taxiapp/keystore.properties.example`
   в `taxiapp/keystore.properties` и заполнить своими значениями — файл уже в
   `.gitignore`, `assembleRelease`/`bundleRelease` подхватит его сами.
3. Google Play принимает `.aab` (`./gradlew :taxiapp:bundleRelease`); RuStore — обычно
   `.apk` через RuStore Console/CLI.
4. Иконка сейчас простая vector-заглушка — перед публикацией нужен нормальный
   дизайн иконки, скриншоты, feature graphic.
5. `versionCode`/`versionName` — увеличивать `versionCode` на каждую новую загрузку.

**Юридическое — важно, это не техническая мелочь:**
6. Такси-агрегаторы регулируются отдельно почти везде — и правила разные по странам.
   Ранее здесь была ссылка на российский закон о такси, но сервис ориентирован на
   Узбекистан — там свои требования к службам заказа такси/агрегаторам (регистрация,
   реестр перевозчиков и т.п.), и они отличаются от российских. Без этого юридически
   нельзя вести реальную (не тестовую) деятельность агрегатора, даже если само
   приложение готово технически — уточнить требования стоит с местным юристом до
   реального запуска, российский ФЗ о такси тут не применяется.
7. Политика конфиденциальности (обязательна для обеих площадок) — понадобится реальный
   текст с описанием, какие данные собираются (геолокация, телефон, платёжные данные и
   т.п.), а не заглушка.
8. Если добавите реальную геолокацию водителя — RuStore и особенно Google Play отдельно
   и строго проверяют доступ к геопозиции в фоне (`ACCESS_BACKGROUND_LOCATION`) — нужно
   обоснование и часто отдельная форма/декларация в консоли разработчика.
